ShuttleFlow: Adding AI to a Booking System

  • Author Alex Nguyen
  • Date November 16, 2026
  • Repository github.com/AlexNguyen7369/ShuttleFlow

ShuttleFlow lets badminton players book courts and coaching sessions. In Milestone 4 it gained three AI features: an assistant that books and cancels through a chat conversation, a background agent that sends each player a personal reminder the day before their session, and a help box that answers questions about the facility's rules using only the official policy document. The main design goal was safety: the AI can do only what a signed-in player could already do, it always asks before changing a booking, and it cannot cause two players to get the same court. After the milestone, sign-in was moved to signed login tokens (JWT) and the website was rebuilt with Next.js; section 12 describes that upgrade.

2 How the pieces fit together

The AI features are added on top of the existing system rather than beside it. Google's Gemini model writes the replies and decides which action to take next, but every action it takes goes through ShuttleFlow's existing booking logic, the same logic the website already uses.

3 The booking assistant (Agent 1)

A signed-in player types requests such as "Book the earliest open court this week" in the Assistant panel. Gemini reads the request and decides which of ShuttleFlow's actions, called tools, to use. The assistant also remembers the conversation, so a follow-up like "actually make it 2pm" works.

ToolWhat it does
Find open slotsLists bookable court or coaching times in a date range, earliest first
List my bookingsShows the player's upcoming appointments
Propose booking / Confirm bookingStep 1 holds a slot choice without booking it; step 2 books it after the player agrees
Propose cancel / Confirm cancelThe same two steps for cancelling
Look up policySearches the policy document for rules, prices and hours

Why the assistant can't break the rules

It only uses existing features

Each tool calls the same booking code the website uses. The assistant cannot reach the database any other way, so every existing check still applies.

It acts as the signed-in player

The assistant always works on behalf of whoever is signed in. It cannot choose to act as someone else, and a court manager's account cannot book through it.

It must ask before booking

Booking is split into two steps. The confirm step works only if the player sent a new message after the proposal, so the AI cannot book on its own, even if it ignores its instructions.

One "yes" books once

A confirmation is used up as soon as it is acted on, and an old proposal expires if the conversation moves on, so a stray "yes" later cannot book anything. The assistant also answers one message at a time per player, so a reply can only confirm a proposal the player has actually seen.

The ask-before-booking rule is enforced in the code, not only in the AI's instructions. The proposal is saved in the database for that player, and this short excerpt is the check that runs before every booking or cancellation:

public Optional<Long> takeConfirmable(long userId, String kind, int turn) {
    Optional<PendingRecord> found = repository.findPending(userId);
    if (found.isEmpty() || !found.get().kind().equals(kind) || found.get().turn() >= turn) {
        return Optional.empty();
    }
    PendingRecord pending = found.get();
    if (pending.turn() != turn - 1) {
        // Stale: the user moved on after the proposal, so this message is not the answer to it.
        repository.clearPending(userId);
        return Optional.empty();
    }
    return repository.claimPending(userId, kind, pending.targetId(), pending.turn())
            ? Optional.of(pending.targetId()) : Optional.empty();
}

The pending choice must be the right kind of action and must come from the player's previous message; claiming it is a single database update, so it can only be used once. Otherwise nothing is booked.

4 Proving the assistant can't double-book

The most important rule in ShuttleFlow is that a court can only be booked by one player at a time. Earlier milestones enforce this in the database itself. Milestone 4 adds a test showing the rule still holds when bookings come through the assistant: two players propose the same court, then both say yes. One booking succeeds, the other is told "Court is already booked.", and the database contains exactly one booking.

void twoSessionsProposeAndConfirmTheSameSlotOnlyOneBooks() {
    UserSession alex = AgentRaceSupport.customer(3L);
    UserSession jamie = AgentRaceSupport.customer(4L);
    tools(alex, 1).proposeBooking(slotId);
    tools(jamie, 1).proposeBooking(slotId);

    String first = tools(alex, 2).confirmBooking();
    String second = tools(jamie, 2).confirmBooking();

    assertThat(first).startsWith("Booked:");
    assertThat(second).isEqualTo("Error: Court is already booked.");
    assertThat(AgentRaceSupport.activeBookings(jdbc, slotId)).isEqualTo(1);
}

The required test, in the player-facing order: both propose, both confirm, one wins.

A second version sends eight confirmations from eight different players at the same instant. It passed on the test database and in every round on a real PostgreSQL database, with exactly one booking each time.

5 The reminder agent (Agent 2)

The reminder agent works without anyone asking it to. Every 15 minutes it:

  1. Looks for bookings that start within the next 24 hours and have not had a reminder yet.
  2. Asks Gemini to write a short, friendly reminder with the player's name, the court or coach, and the start time.
  3. Fact-checks the message (see section 7). If the check fails, or Gemini is unavailable, it uses a plain standard message instead.
  4. Hands the message to the notification system from Milestone 3, which delivers it and retries if the notification service is down.

Each booking gets at most one reminder, even if the agent runs again or two runs overlap. A court manager can also start a run with the Run reminders now button, which is useful for demos.

6 The policy help box (RAG)

Players can ask questions like "Can I cancel a booking?" or "How much is coaching?". Instead of letting the AI answer from general knowledge, which could produce invented rules, ShuttleFlow uses retrieval-augmented generation (RAG):

  1. A hand-written policy and FAQ document covers hours, courts and coaches, prices, booking and cancellation rules, reminders, equipment and contact details.
  2. When the app starts, the document is split into sections and indexed so the most relevant sections can be found for any question.
  3. For each question, the three closest sections are given to Gemini with the instruction to answer only from them and to say "I don't know" otherwise.
  4. The answer is shown together with the names of the sections it came from.

An automated test checks that the prices in the policy document match the prices in the database, so the document cannot quietly go out of date. The booking assistant uses the same search when a player asks it a policy question mid-conversation.

7 Bonus: the reminder agent checks its own work

AI models can write a confident, friendly message that contains the wrong time or the wrong court. Before any reminder is sent, ShuttleFlow compares the message with the actual booking: it must name the correct court or coach and the exact start time, and it must not contain leftover placeholders such as "[name]" or any links. If anything is off, the player receives the plain standard message instead, so wrong information never reaches them. The system also counts how many reminders were sent and how many needed the fallback, which shows whether the AI is becoming unreliable.

9 Keeping the API key safe

The Gemini key, and since the upgrade the secret that signs login tokens, are read from environment variables and stored in a local file that is never committed to GitHub; a scan of the project history found no key. If no key is set, ShuttleFlow still runs normally: the AI features reply that they are unavailable, and reminders use the standard message. Logs never record the key, the player's messages or the AI's replies.

10 Testing

The project has 146 automated tests. The AI tests replace Gemini with a stand-in that gives fixed answers, so they run quickly, cost nothing and never need the real key. They cover:

  • the double-booking test above, including a version with eight simultaneous players;
  • the ask-before-booking rule: no booking without a proposal, no booking in the same message, no repeated bookings from one "yes";
  • sign-in and role checks for every AI feature;
  • policy answers using the right document sections, and the document matching the database;
  • one reminder per booking, the fallback message, and the fact-check catching wrong times and courts;
  • since the upgrade, login tokens: forged, tampered, expired and unsigned tokens are all rejected.

GitHub runs the full test suite and builds the website automatically on every change.

11 Problems found while testing with the real AI

  • Replies were cut off. Gemini sometimes sends an answer in several pieces, and only the first piece was being shown. All pieces are now joined.
  • The assistant asked "confirm?" too early. Once, it asked for confirmation before recording the proposal, so the player's "yes" produced a second question instead of a booking. The safety check worked as designed (nothing was booked by mistake), and the assistant's instructions were tightened.
  • A code review found gaps in the fact-check (it accepted "11pm" for a 1pm booking) and in how long a proposal stayed valid. Both were fixed and covered by new tests.

12 After Milestone 4: signed login tokens and a Next.js website

Once the AI features were finished, two parts of the system were upgraded on a separate branch, reviewed, and merged.

During Milestone 4After the upgrade
How the server knows who you areThe server kept a session for each signed-in playerThe server signs a login token (a JWT) and keeps nothing; each request carries the token
Where the login lives in the browserA session cookieThe token, in a cookie the page's own scripts cannot read
The assistant's memory of a pending bookingKept in the player's sessionKept in a database table, one row per player
The websitePlain HTML, CSS and JavaScript filesA Next.js (React) app with the same pages

Why signed tokens

With a token, the server does not have to remember who is signed in: it checks the token's signature on every request. The token holds the player's id and role, is signed with a secret only the server knows, and expires after two hours. It is stored in a cookie marked HttpOnly, so even a malicious script injected into the page could not read it, and SameSite, so other websites cannot use it to send requests. The server accepts only one signing method, which blocks a known attack where a forged token claims to need no signature.

The tradeoff is that a token cannot be cancelled early. Signing out deletes the cookie from the browser, but a copied token would stay valid until it expires, which is why its lifetime is kept short.

What it meant for the AI features

The booking assistant used to remember its pending proposal and turn number in the player's session. With no sessions, that information moved to a database table. The safety rules did not change: a confirmation must still answer the previous message, it can still be used only once, and the assistant still acts only as the signed-in player. All the earlier tests, including the double-booking test, pass unchanged in what they check.

The Next.js website

The website was rebuilt with Next.js, keeping every page: home, sign in, browse and book, my bookings, the provider workspace and the assistant. The browser only ever talks to the Next.js server, which forwards data requests to the booking API. Because of that, the login cookie belongs to the same site as the pages, and the page code never handles the token itself. If a token expires while the page is open, the site shows the player as signed out.

Reviewing the change

Before merging, a code review found three real problems, all fixed with new tests: two first requests from the same player arriving at once could fail on PostgreSQL; two chat messages sent at once could let one confirm a proposal the player had not seen; and the website kept showing a player as signed in after their token expired.

13 Limitations and next steps

  • The chat history the assistant remembers is kept in memory and resets when the server restarts; only the pending proposal and turn number are in the database. Saving the history there too would fix this.
  • A login token stays valid until it expires, even after signing out, and the assistant's one-message-at-a-time rule assumes a single server.
  • The free Gemini tier limits how many requests can be made. During a burst of use the assistant may be briefly unavailable, and reminders fall back to the standard message.
  • The fact-check verifies the court and time but not the day.
  • The hours, equipment and contact details in the policy document are sample data for the course project.
