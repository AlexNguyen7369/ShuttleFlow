# Milestone 3 Implementation Plan

Companion to `Milestone3/m3-checklist.md` (the checklist tracks what is done;
this file says how to build it). Written 2026-10-27. Nothing here is built yet.

## Design summary

- **Transactional outbox.** `book()` and `cancel()` write a `notifications` row
  (`PENDING`) in the same transaction as the booking, so a rollback sends
  nothing and a crash right after commit loses nothing.
- **After-commit fast path.** An async after-commit listener sends the row
  right away. The HTTP call never holds the slot lock or slows the booking response.
- **Poller backstop.** A scheduled job resends `PENDING` rows older than ~60s.
- **Bounded retry.** Timeouts are 1s connect / 2s read. Each round makes up to
  3 attempts with backoff, retrying only on timeout, refused connection or 5xx.
- **Dead-letter state.** A 4xx, or 5 failed rounds, marks the row `FAILED`,
  so it is never resent forever.
- **Idempotency key.** The key is `BOOKED:<appointmentId>` or
  `CANCELLED:<appointmentId>`. The mock service stores each key once, so
  duplicate sends are harmless.
- **Self-contained message.** One coarse-grained call carries an immutable DTO
  (`recipient`, `type`, `message`, `idempotencyKey`, `appointmentId`). The
  receiver never sees DB rows.


### Notification flow

```
book()/cancel()  [one transaction]
  ├─ existing writes (appointment + slot status)
  ├─ NotificationService.enqueue(...)  → INSERT notifications row, status PENDING
  └─ publish NotificationQueuedEvent(notificationId)
COMMIT ──► @Async @TransactionalEventListener(AFTER_COMMIT) → dispatcher.dispatch(id)   (fast path)
@Scheduled every 30s → rows PENDING and created_at < now-60s → dispatch(id)          (backstop)
dispatch(id): gateway.send(request) → SENT | RETRYABLE | PERMANENT
   SENT → status SENT;  PERMANENT (4xx) → FAILED;  RETRYABLE → attempts+1, stays PENDING,
   FAILED once attempts reach 5
```

`@Async` keeps the booking response fast even when the service hangs (3 × 2s timeouts). It is
safe because the outbox row already exists. Duplicate sends (fast path and poller racing) are
absorbed by the idempotency key; status updates use `WHERE status = 'PENDING'`.

### Step 1 — Schema (`src/main/resources/schema.sql`)

Add `DROP TABLE IF EXISTS notifications CASCADE;` first, and the table last:

```sql
CREATE TABLE notifications (
    notification_id  BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    appointment_id   BIGINT NOT NULL REFERENCES appointments(appointment_id),
    idempotency_key  VARCHAR(64)  NOT NULL UNIQUE,   -- BOOKED:57 / CANCELLED:57
    type             VARCHAR(30)  NOT NULL CHECK (type IN ('BOOKING_CONFIRMED', 'BOOKING_CANCELLED')),
    recipient        VARCHAR(255) NOT NULL,
    message          VARCHAR(500) NOT NULL,
    status           VARCHAR(20)  NOT NULL DEFAULT 'PENDING' CHECK (status IN ('PENDING', 'SENT', 'FAILED')),
    attempts         INT          NOT NULL DEFAULT 0 CHECK (attempts >= 0),
    created_at       TIMESTAMP    NOT NULL DEFAULT CURRENT_TIMESTAMP,
    last_attempt_at  TIMESTAMP
);
```
Portable for H2 + PostgreSQL. Update `docs/schema-notes.md`.

### Step 2 — DTO and config

- `dto/NotificationRequest` — immutable: `recipient`, `type`, `message`, `idempotencyKey`, `appointmentId`.
- `application.properties` (and the test copy):
  `shuttleflow.notification.base-url=${NOTIFICATION_BASE_URL:http://localhost:8080}`,
  `connect-timeout-ms=1000`, `read-timeout-ms=2000`, `max-attempts=3`, `poll-ms=30000`,
  `stale-after-seconds=60`, `max-rounds=5`.
  Test properties: base-url `http://127.0.0.1:1` (instant refusal) and a huge `poll-ms`.

### Step 3 — Mock notification service

- `controller/MockNotificationController` `POST /mock-notifications` → `service/MockNotificationService`.
- In-memory `ConcurrentHashMap<String, NotificationRequest>`; `putIfAbsent` on `idempotencyKey`.
- Blank `recipient`/`type`/`message`/`idempotencyKey` → `InvalidRequestException` (400 through
  the existing `ApiExceptionHandler`). New → 202, duplicate → 200, both with no body leak.
- Logs `Mock notification received key=...` (never the message body or recipient).

### Step 4 — Gateway (`service/NotificationGateway`)

- `RestClient` (in `spring-boot-starter-web`) built with `SimpleClientHttpRequestFactory` timeouts.
- `SendResult send(NotificationRequest)` — never throws.
- Up to `max-attempts` tries, backoff 200ms then 400ms. Retry on `ResourceAccessException`
  (timeout, refused) and `HttpServerErrorException` (5xx). `HttpClientErrorException` (4xx) →
  `PERMANENT` right away.
- Logs: INFO `Notification sent key=BOOKED:12 attempt=1`; WARN `Notification attempt 2/3 failed
  key=BOOKED:12: Read timed out`; ERROR `Notification gave up after 3 attempts key=BOOKED:12`.
- `SendResult` is a small enum in `service/` (`SENT`, `RETRYABLE`, `PERMANENT`).

### Step 5 — Outbox repository + service

- `repository/NotificationRepository`: `insert(...)` returning id, `findById`, `findDue(cutoff, limit 50)`
  (`status = 'PENDING' AND created_at < ? ORDER BY notification_id LIMIT ?`), `markSent(id)`,
  `markFailed(id)`, `recordAttempt(id, now)`. All guarded with `AND status = 'PENDING'`; `?` params only.
- `service/NotificationService`:
  - `enqueue(appointmentId, type, recipient, AppointmentDto details)` — builds key
    (`BOOKED:`/`CANCELLED:` + id) and the readable message ("Your Singles at Court 3 on Sat
    10:00 is booked."), inserts, then publishes `NotificationQueuedEvent` via `ApplicationEventPublisher`.
  - `dispatch(id)` — load the PENDING row, call the gateway, apply the status transition, update metrics.
  - `@Async @TransactionalEventListener(phase = AFTER_COMMIT) onQueued(event)` → `dispatch`.
  - `@Scheduled(fixedDelayString = "${shuttleflow.notification.poll-ms}") sendDue()` → `findDue` → `dispatch` each.
- `NotificationQueuedEvent` — record in `service/`.
- `ShuttleflowApplication`: add `@EnableAsync @EnableScheduling`.

### Step 6 — Hook into booking (`service/AppointmentService`)

- Constructor gains `NotificationService` and `MetricsService`.
- `book()`: after the `AppointmentDto` is read, call `enqueue(id, BOOKING_CONFIRMED, user.getEmail(), dto)`.
  It runs inside the transaction, so a rollback removes the row and no event fires.
- `cancel()`: after the slot reopens, load the details with the existing
  `appointmentRepository.findCustomerAppointment(appointmentId, user.getUserId())` and call
  `enqueue(..., BOOKING_CANCELLED, user.getEmail(), dto)`.
- Logs: INFO `Booking created appointmentId=.. slotId=.. userId=..`, `Booking cancelled appointmentId=..`;
  WARN `Booking conflict slotId=..`.
- Update the constructors in `BookingServiceUnitTest` (mock the two new collaborators).

### Step 7 — Health (`/health`)

- `repository/HealthRepository.ping()` runs `SELECT 1`; `service/HealthService` catches
  `DataAccessException` → DOWN, logs ERROR `Health check: database unreachable`.
- `controller/HealthController` → `dto/HealthDto(status, database)`: 200 UP / 503 DOWN.

### Step 8 — Metrics (`/metrics`)

- `service/MetricsService`: `AtomicLong` counters `bookingsCreated`, `bookingConflicts`,
  `notificationsSent`, `notificationFailures`, plus `pendingNotifications` read from the repository count.
- `controller/MetricsController GET /metrics` → `dto/MetricsDto`. Plain counters, no Actuator.

### Step 9 — Tests (`src/test/java/com/shuttleflow/`)

- `service/NotificationGatewayTest` (plain JUnit + JDK `com.sun.net.httpserver.HttpServer` stub, real HTTP):

  sleeps past the read timeout → RETRYABLE after 3 hits; dead port → RETRYABLE.
- `service/NotificationServiceTest` (mocked repo + gateway): RETRYABLE → attempts+1, stays PENDING;

- `controller/MockNotificationControllerTest` (MockMvc): new → 202; same key twice → 200, stored once; blank recipient → 400.
- `controller/NotificationIntegrationTest` (`@SpringBootTest`, dead-port base-url): **required test** —
  book → 201, one active appointment, one `BOOKED:<id>` PENDING row; cancel with service down →

- `controller/HealthControllerTest`: UP → 200; `@MockBean HealthRepository` throwing → 503 DOWN.
- `controller/MetricsControllerTest`: a booking bumps `bookingsCreated`.
- `BookingServiceUnitTest`: enqueue called on success, never on conflict.
